> Auditoría READ-ONLY. Toda clasificación justificada leyendo el CUERPO del archivo (no nombre/firma). Cita `file:line` del cuerpo real.
> Clasificación: **1 = real y funcional** · **2 = parcial / stub-parcial / no-op interno / MVP-truncado** · **3 = ausente / sólo copy / sólo modelo sin servicio**.

## Respuesta GLOBAL (modelo per-proyecto de las 73 medidas)

**SÍ existe** un modelo per-proyecto que lista las 73 medidas, marca aplicable/no-aplicable con justificación y refuerzos por categoría: la tabla `dda_entries`, generada atómicamente por `m03_dda/service.py:71-168` (`generate_dda`). Para cada `EnsMeasure`: si aplica → entry `NO_VALORADO` + refuerzos leídos por categoría (`_applicable_reinforcements` líneas 484-505, cruzando `ens_measure_refuerzos.applicable_categories ? :cat`); si no aplica → `NO_APLICA` + justificación template (`render_no_aplica_justification`). Aplicabilidad escalada por categoría vía `_measure_applies` (líneas 466-482) sobre columnas `aplica_basica/media/alta`. Freeze/unfreeze (`aprobado_por`+`fecha_aprobacion`, líneas 299-367) con gate ≥80% valoradas.

**Matices importantes (no es un control-model completo):**

1. **NIVEL DE MADUREZ (CMM) — dualidad incoherente.** `dda_entries.estado_implementacion` es un modelo de **4 estados** (`no_valorado/no_implantada/parcial/implantada`), NO CMM L1-L5. El CMM L0-L5 real **sí existe pero vive en OTRO motor**: `m04_gap/enums.py:23-66` (`ControlState` L0-L5, `CATEGORY_TARGET_LEVEL` BASICA→L2 / MEDIA→L3 / ALTA→L4 según CCN-STIC 808). El gap-engine compara estado_actual vs estado_objetivo escalado por categoría (`m04_gap/service.py:588`). Pero ese nivel objetivo/actual vive en `Finding.metadata_jsonb` (`estado_actual`/`estado_objetivo`), **no en la entry DdA**. Resultado: la SoA y el motor de madurez no comparten el campo de nivel.

2. **EVIDENCIA POR MEDIDA — sí enlazada.** `m07_evidence/ingestion_service.py:80-167` valida `measure_code` contra `ens_measures`, persiste `evidence.measure_id` + `measure_code` + `control_id` (NULL) + SHA-256 + firma Ed25519 + cola antivirus. Por tanto evidencia ↔ medida es real, pero el enlace canónico es `evidence`/`documents`, no un campo en `dda_entries`.

3. **SEMÁFORO POR MEDIDA — STUB no-op.** `m04_gap/control_status_service.py:112-119`: el filtro por `measure_code` es un `pass` con comentario *"Simplified: match ALL documents project mientras compute MVP"*. `compute_control_status` calcula el semáforo sobre **TODOS** los documentos del proyecto, NO sobre los de esa medida → cualquier medida consultada devuelve el mismo agregado. Clase 2: prevención de false-green correcta pero sin granularidad por medida (riesgo de falso-verde/falso-rojo cruzado entre medidas).

**Veredicto global:** la SoA/DdA es real y certificable como registro; el "control-model con nivel CMM + evidencia + semáforo, todo por medida" está **repartido entre 3 motores y con un eslabón (semáforo per-medida) en stub**.

## Prosa: hueco normativo real vs hueco de producto · prioridad de bloqueo

### Lo que está REAL y certificable (clase 1, no bloquea)
- **SoA / DdA per-proyecto (las 73 medidas)**: generación atómica, aplicabilidad por nivel, refuerzos por categoría, no_aplica con justificación, freeze/unfreeze con gate de completitud, audit_log. Es el corazón ENAC y está sólido (`m03_dda/service.py`).
- **Fábrica documental (org.1-4 + 96 plantillas)**: docxtpl con datos del cliente + Ed25519 + PDF + gate DdA-congelada + audit_log `document.generated`. Genera PSI, Normativa, POS, contratos reales (`m06_document_factory/service.py:267-436`).
- **Evidencia ↔ medida**: ingesta con `measure_code` validado, SHA-256, firma, antivirus (`m07_evidence/ingestion_service.py:80-167`).
- **Firma-e (mp.info.3)**, **gap-engine CMM L0-L5 por categoría (CCN-STIC 808)**, **cambios/materialidad (op.exp.5)**, **cláusulas ENS a terceros (op.ext.1, C-130 CCN-STIC 823)**, **BIA (op.cont.1)**, **formación con registro (mp.per)**, **MFA/privilegios detectados en cloud (op.acc.5/6)**, **vuln-scan con IDMS (mp.s.2)**.

### HUECO DE PRODUCTO (la medida se cubre documentalmente; falta verificación/automatización técnica)
La mayoría de familias técnicas (op.exp.2/3/10, mp.if, mp.eq, mp.com, mp.si, mp.s.4, op.mon detección-intrusión, mp.info.4 TSA, mp.info.6 backup del cliente) se cubren con **plantilla + entry DdA + evidencia subida manualmente**. Para certificación MEDIA esto es **suficiente** (el ENS no exige que la consultora ejecute la medida técnica del cliente; exige documentarla, implantarla y evidenciarla). No bloquea.

### HUECO NORMATIVO con riesgo (clase 2/3 que conviene cerrar antes de certificar)
1. **op.exp.8 (clase 3) — el más serio**: retención de logs ≥12 meses + NTP no se rastrea como medida del cliente; sólo aparece en copy/preguntas. Para MEDIA es medida aplicable y un auditor ENAC lo pregunta. **Mitigación**: se puede cubrir vía DdA + evidencia manual (captura de config de retención + NTP), pero hoy no hay artefacto/verificación dedicada. **No bloquea formalmente** (la DdA lo lista), pero es el gap más expuesto.
2. **Semáforo per-medida (clase 2) — `control_status_service.py:112-119` stub no-op**: el cálculo de cumplimiento por medida agrega TODOS los documentos del proyecto en vez de filtrar por `measure_code`. Riesgo de falso-verde/rojo cruzado en el dashboard de control. No bloquea la firma, pero degrada la fiabilidad del panel de conformidad por medida.
3. **Dualidad nivel-de-madurez (clase 2)**: `dda_entries.estado_implementacion` (4 estados) vs CMM L0-L5 en `m04_gap` (en `Finding.metadata_jsonb`). El nivel objetivo por categoría (L2/L3/L4) NO se materializa en la entry DdA. Coherente pero fragmentado; un auditor que pida "nivel de madurez por medida" lo obtiene del gap-engine, no de la SoA.
4. **op.acc.6 MFA — no escala rol/nivel (clase 2)**: detecta `mfa_enabled False` pero no distingue "admins en Media" vs "todos en Alta". Sobre-reporta o infra-reporta según el nivel objetivo.
5. **mp.info.6 (clase 2)**: m26 respalda a FULKRO, no al cliente. La copia del cliente es documental + evidencia. Correcto para el modelo de negocio, pero conviene que el discurso ante ENAC sea explícito.

### Veredicto de bloqueo para certificar MEDIA
**No hay bloqueante duro de producto.** La SoA + fábrica documental + evidencia-por-medida + firma + gap-engine cubren el ciclo certificable. Los huecos son: (1) **op.exp.8** (cerrar con evidencia manual + idealmente un check), y (2) **el stub del semáforo per-medida** (fiabilidad del dashboard, no del expediente). Ambos son atajables sin rediseño. Para **ALTA**, los gatings SOLO-ALTA (op.ext.3, op.cont.2-4, mp.eq.3, mp.info.4) se activan correctamente vía aplicabilidad DdA, pero mp.info.4 (sellos de tiempo / TSA) carece de integración real → ahí sí habría que documentar muy bien o integrar TSA antes de un cliente ALTA.
